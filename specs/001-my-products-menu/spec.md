# Feature Specification: 我的产品栏目（小纸条 PP-Writer / 跑步 PP-Runner）

**Feature Branch**: `001-my-products-menu`

**Created**: 2026-10-11

**Status**: Done（2026-10-11 验收通过）

**Input**: User description: "增加 我的产品 栏目，下拉菜单：小纸条（PP-Writer）、跑步（PP-Runner）。每个产品介绍三部分：1、产品介绍：https://mubu.com/home 2、下载：https://mubu.com/apps 3、新功能：https://mubu.com/doc/d5501245199?autoHide=1 。新功能的内容取我另一个 claude code 项目 pp-cloud 下的开发历史或者 spec"；补充：「再增加一个 Releases 的栏目（参考：https://www.notion.com/releases，相当于新功能的详细版本）」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从导航进入产品页了解产品 (Priority: P1)

访客打开个人网站，在顶部导航看到「我的产品」，悬停或点击后展开下拉菜单，里面有「小纸条（PP-Writer）」和「跑步（PP-Runner）」两项。点击其中一项，进入该产品的介绍页，第一部分「产品介绍」说明这个产品是什么、解决什么问题、有哪些核心能力。

**Why this priority**: 没有导航入口和产品介绍，整个栏目就不存在；这是最小可用版本。

**Independent Test**: 只完成导航和两个产品页的「产品介绍」部分，就能让访客从首页两次点击内看懂两个产品分别是什么。

**Acceptance Scenarios**:

1. **Given** 访客在网站任意页面，**When** 查看顶部导航，**Then** 看到「我的产品」一项，位置在「博客」和「关于」之间或之后，与现有菜单风格一致
2. **Given** 访客在桌面浏览器，**When** 悬停/点击「我的产品」，**Then** 展开下拉菜单，依次显示「小纸条（PP-Writer）」「跑步（PP-Runner）」
3. **Given** 访客在手机上，**When** 打开折叠菜单并点开「我的产品」，**Then** 同样能看到并点进两个产品
4. **Given** 访客点击「小纸条（PP-Writer）」，**When** 页面打开，**Then** 看到产品名称、一句话定位，以及「产品介绍」「下载」「新功能」三个部分，可在页内快速跳到任一部分

---

### User Story 2 - 获取下载方式 (Priority: P2)

访客看完介绍，想试用产品，在产品页的「下载」部分找到各平台（小纸条：Android、macOS 桌面版；跑步：Android）的获取方式。

**Why this priority**: 介绍之后的自然下一步是下载使用，但下载渠道依赖分发方式，可以晚于介绍上线。

**Independent Test**: 在产品页「下载」部分，按平台列出获取方式，每一项都能点开或清楚说明如何获取。

**Acceptance Scenarios**:

1. **Given** 访客在小纸条产品页，**When** 查看「下载」部分，**Then** 按平台（Android、macOS）分别列出获取方式、当前版本号和更新日期
2. **Given** 某个平台暂未公开提供下载，**When** 访客查看该平台，**Then** 显示明确的「暂未开放」或获取说明，而不是失效链接

---

### User Story 3 - 浏览新功能（更新日志） (Priority: P3)

关注产品进展的访客，在产品页「新功能」部分按时间倒序看到近期上线的功能和修复，每条一句话说明对用户的价值。

**Why this priority**: 体现产品在持续迭代，但内容需要从开发历史中整理，工作量最大，放在最后。

**Independent Test**: 「新功能」部分按时间倒序列出条目，每条都有日期和面向用户的描述，且不包含任何内部信息。

**Acceptance Scenarios**:

1. **Given** 访客在小纸条产品页，**When** 查看「新功能」部分，**Then** 按时间倒序（按月或按版本分组）看到功能条目，每条含日期和一句话用户价值描述
2. **Given** 原始开发记录里有服务器地址、内部 IP、证书、账号、内部脚本、纯调试类修改，**When** 整理成新功能条目，**Then** 这些内容一律不出现在页面上
3. **Given** 跑步产品页，**When** 查看「新功能」部分，**Then** 只包含与跑步 App 相关的条目，不混入小纸条的内容（反之亦然）

---

### User Story 4 - 查看 Releases 详细版本说明 (Priority: P4)

想深入了解某次更新的访客，从产品页「新功能」底部的「查看全部 Releases」进入该产品的 Releases 页面。页面参考 Notion Releases 的形式：按时间倒序列出每一次发布，每次发布有标题、日期、一段概述，以及若干个功能小节（每个小节有小标题、几句说明，有合适截图时附图）。点开某次发布可以看到完整的详细说明，并有固定网址可以分享。

**Why this priority**: 「新功能」是摘要，Releases 是它的详细版本；先有摘要再补详细说明，单独上线也有价值。

**Independent Test**: 进入小纸条的 Releases 页面，能看到按时间倒序的发布列表，点开任一发布能看到它包含的全部功能小节，且内容与「新功能」中对应条目一致、更详细。

**Acceptance Scenarios**:

1. **Given** 访客在产品页「新功能」部分，**When** 点击「查看全部 Releases」，**Then** 进入该产品的 Releases 列表页
2. **Given** 访客在 Releases 列表页，**When** 浏览，**Then** 按时间倒序看到每次发布的标题、日期和概述
3. **Given** 访客点开某一次发布，**When** 页面打开，**Then** 看到该次发布的全部功能小节（小标题 + 说明，可选截图），并可返回列表或进入上一次/下一次发布
4. **Given** 「新功能」中的一条摘要，**When** 访客想看详情，**Then** 能跳到 Releases 中对应的那次发布

---

### Edge Cases

- 一条开发记录同时涉及两个产品（如「pp-runner + pp-writer + web」），按受益产品分别写入，或只写入主要受益的产品，不重复堆砌技术细节
- 大量连续的修复类记录（如十几个 fix）合并为一条「若干稳定性修复」，避免日志刷屏
- 产品只有一个平台时，「下载」部分不显示其他平台的空占位
- 访客从手机访问：下拉菜单、三部分跳转、长更新列表都可正常浏览，没有横向滚动
- 产品页地址被直接分享：打开后能独立看懂，不依赖从首页进入

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 网站顶部导航 MUST 新增「我的产品」一项，且为下拉菜单，包含「小纸条（PP-Writer）」「跑步（PP-Runner）」两个子项
- **FR-002**: 每个产品 MUST 有独立的介绍页面，有固定、可分享的网址
- **FR-003**: 每个产品页 MUST 包含三个部分，顺序为：产品介绍、下载、新功能；页面顶部提供跳到三部分的快捷入口
- **FR-004**: 三个部分的版式 MUST 参考幕布对应页面，但内容全部是自己的产品：「产品介绍」参考 mubu.com/home（大标题 + 核心能力卡片），「下载」参考 mubu.com/apps（按平台分块），「新功能」参考幕布更新日志（按时间倒序的条目列表）；页面上不链接到幕布
- **FR-005**: 「产品介绍」MUST 包含：产品名称（中英文）、一句话定位、3–6 个核心能力点、支持的平台
- **FR-006**: 「下载」MUST 按平台列出获取方式、版本号和更新日期；当前阶段两个产品都不提供公开下载：每个平台显示「内测中，暂未开放下载」及联系方式（联系方式沿用网站「关于」中已有的）
- **FR-007**: 「新功能」MUST 以 pp-cloud 项目的开发历史/spec 为素材，整理成面向普通用户的条目，按时间倒序展示
- **FR-008**: 「新功能」条目 MUST NOT 包含服务器地址、IP、域名、证书、密钥、账号、内部脚本名、人员姓名等内部信息，也不包含纯开发调试类内容
- **FR-009**: 「新功能」和 Releases 内容 MUST 一次性整理 pp-cloud 现有的全部相关历史；之后由站长手动触发重新整理，每次发布前人工把关，不做自动同步
- **FR-010**: 新栏目 MUST 与网站现有的中文界面、配色、明暗模式保持一致，在手机和桌面上都可正常使用
- **FR-011**: 新增栏目 MUST NOT 影响现有首页、博客、关于页面的显示
- **FR-012**: 每个产品 MUST 有一个 Releases 页面，版式参考 Notion Releases：按时间倒序列出每次发布（标题、日期、概述），每次发布有独立、可分享的详情页，包含若干功能小节（小标题、说明、可选截图）
- **FR-013**: 「新功能」部分底部 MUST 提供「查看全部 Releases」入口；「新功能」的每条摘要 MUST 能跳到 Releases 中对应的那次发布
- **FR-014**: Releases 与「新功能」MUST 来自同一份整理结果、内容一致：「新功能」是一句话摘要，Releases 是详细说明；FR-008 的内部信息过滤同样适用于 Releases

### Key Entities

- **产品（Product）**：名称（中文/英文）、一句话定位、核心能力、支持平台、对应页面
- **下载项（Download）**：所属产品、平台、获取方式（链接或说明）、版本号、更新日期
- **发布（Release）**：所属产品、标题、日期、概述、包含的功能小节；一次发布对应「新功能」中的一组摘要条目
- **功能小节（Release Item）**：所属发布、分类（新功能 / 改进 / 修复）、一句话摘要（用于「新功能」）、详细说明（用于 Releases）、可选截图

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 访客从网站任意页面最多 2 次点击就能进入任一产品页
- **SC-002**: 两个产品页都完整包含三部分，没有空白或「待补充」的部分；两个产品都有 Releases 页面，「新功能」中的每条摘要都能在 Releases 里找到对应的详细说明
- **SC-003**: 「新功能」和 Releases 中公开发布的所有内容逐条人工检查，内部信息泄露为 0 条
- **SC-004**: 产品页在手机（宽度 375px）和桌面上都能完整浏览，没有错位或横向滚动
- **SC-005**: 新栏目上线后，原有首页、博客、关于页面的显示和链接 100% 保持不变
- **SC-006**: 第一次访问的人读完「产品介绍」后，能用一句话说出产品是做什么的

## Assumptions

- 小纸条（PP-Writer）是写作笔记 App，平台为 Android 和 macOS 桌面版；跑步（PP-Runner）是跑步记录 App，平台为 Android（来自 pp-cloud 项目目录与开发记录）
- 「新功能」的素材范围：pp-cloud 中带 `[pp-writer]`、`[pp-runner]` 标签的 spec 目录和对应 git 提交记录；纯 Web 后台（`[web]`/`[backend]`/`[frontend]`）且用户无感知的改动不收录
- 网站是公开访问的，pp-cloud 是私有开发项目，所以对外内容需人工把关后再发布
- 网站仅中文，不做英文版
- pp-cloud 的 App 版本号基本没变（移动端 1.0.0、桌面版 0.1.0），因此「发布」不按版本号划分，而是按时间段或功能批次合并（例如按周或按一组相关 spec）；如果以后有正式版本号，再改为按版本划分
- Releases 是每个产品各自一个，入口在产品页内，不在顶部导航里单独占一项
- 产品截图/图标如有需要，从 pp-cloud 项目中现有资源选取；没有合适的就先不放图
